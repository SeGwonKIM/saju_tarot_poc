# 상용 전환 설계 — PoC 다음에 무엇이 필요한가

> 과제요구사항의 발전 항목 — *"PoC에서 실제 도입까지 필요한 것(데이터, 비용, 운영 방식)을
> 정리해 다음 단계 제안서로 만들어 보세요."*
>
> 작성 2026-09-23 · 근거는 `개선효과검증결과.md` 의 실측값

---

## 0. 이 문서의 범위

상용 서비스의 **설계·안전·개인정보** 부분만 담는다.
수익모델·가격·경쟁사 실명 분석은 **비공개 저장소에 따로 둔다** — 이 저장소는 공개다.

| 담는 것 | 안 담는 것 |
|---|---|
| 주문 처리와 발송 흐름 | 수익모델·가격 |
| 계정 구조와 재열람 | 경쟁사 실명과 개별 분석 |
| 개인정보·안전 설계 | 사업 로드맵 |
| PoC 자산의 이관 계획 | |

## 1. 계정을 만들지 않는다

### 결론

**회원가입·로그인·비밀번호를 만들지 않는다.** 결제할 때 받은
**주문번호 + 전화번호**로 결과를 다시 본다.

### 어떻게 여기까지 왔나

| 단계 | 안 | 왜 접었나 |
|---|---|---|
| 처음 | 이메일 + 비밀번호 | 주 이용층이 40~60대다. 비밀번호 관리가 부담 |
| 중간 | 휴대폰 번호 인증(SMS) | 나쁘지 않으나, **가입 자체가 필요한가**를 안 물었다 |
| **지금** | **가입 없음** | 시장 조사 결과 같은 업종에서 가입 없이 운영하는 사례를 확인했다 |

> **물음이 바뀐 것이 핵심이다.** "인증을 어떻게 할까"가 아니라 "가입이 필요한가"였다.

### 왜 가입을 없애나

| 이유 | 설명 |
|---|---|
| 이탈 | 한 번 보고 마는 손님이 많다. 가입 문턱이 곧 결제 전환율이다 |
| 지킬 것이 준다 | 비밀번호가 없으면 유출될 비밀번호가 없다. 계정이 없으면 탈취도 없다 |
| 이미 받는 정보 | 결제하려면 어차피 이름과 전화번호를 받는다. 그걸 열쇠로 쓴다 |

### 위험은 사라지지 않고 **한 곳으로 모인다**

"내 결과를 남이 보면 어쩌나"가 전부 재열람 경로로 온다.

| 위험 | 막는 법 |
|---|---|
| **주문번호 추측** | **난수로 만든다.** 순번을 쓰면 전화번호 하나만 알아도 남의 결과가 열린다 |
| 전화번호 대입 | 주문번호와 전화번호가 **둘 다** 맞아야 열린다 + 시도 횟수 제한 |
| 문자를 남이 봄 | 문자에 **결과 본문을 넣지 않는다.** 만료가 있는 링크만 보낸다 |
| 번호 재배정 | 통신사가 해지 번호를 재배정한다. 조회 가능 기간을 정한다 (기본 6개월) |
| 주문번호 분실 | 전화번호로 재발송. **이 경로도 횟수 제한 대상** |

### 전화번호 저장 — 암호화하면 검색이 안 된다

| 칸 | 무엇 |
|---|---|
| `phone_enc` | AES-256-GCM 암호문. 문자 보낼 때만 푼다 |
| `phone_lookup` | 정규화 후 **서버 키를 섞은** 해시. 조회용 |

`010-1234-5678` 과 `01012345678` 이 같아야 하므로 정규화가 먼저다.
키를 섞는 이유는 번호가 11자리뿐이라 **그냥 해시하면 전부 역산되기** 때문이다.

### 본인확인(PASS)을 쓰지 않는다

| | SMS 인증 | 본인확인 | **채택** |
|---|---|---|---|
| 확인하는 것 | 번호 소유 | 본인 여부 | — (결제 시 이름·번호를 받음) |
| 받는 정보 | 전화번호 | + 이름·생년월일·성별·CI/DI | 결제에 필요한 것만 |
| 계약 | 문자 발송사 | 본인확인기관 | PG 사만 |

사주가 생년월일을 받긴 하지만 그건 **상담 입력값**이지 본인확인 항목이 아니다.
본인확인으로 오는 생년월일은 주민등록 양력이라 **출생 시각이 없어** 결국 다시 물어야 한다.

⚠ 업종별 본인확인 의무 여부는 **확인하지 않았다.** 유료 전환 전에 확인이 필요하다.

## 2. 주문 처리와 발송 흐름

```
결제 → 초안 생성(몇 초) → 게이트 검사 → 관리자 검수함
     → 30분 뒤 자동 발송 → 문자·알림톡 안내 → 홈페이지 재열람
```

**30분은 계산을 기다리는 시간이 아니다.** 계산은 몇 초면 끝난다.
**관리자가 볼 수 있게 열어 두는 시간**이다.

### 주문 상태

| 상태 | 뜻 | 다음 |
|---|---|---|
| `paid` | 결제 완료 | `drafting` |
| `drafting` | 계산 + 문장 생성 중 | `review` · `held` |
| `review` | 초안이 나왔고 **타이머가 돈다** | `sent` · `held` |
| `held` | 위험 판정 또는 관리자가 멈춤. **타이머 정지** | `review` · `sent` |
| `sent` | 발송 완료 | (끝) |
| `send_failed` | 발송 실패 | 재시도 2회 → `held` |

**보류는 취소가 아니다.** 타이머만 멈춘다.

### 자동 발송에서 빼는 조건 — **코드가 판정한다**

사람이 매번 "이건 위험한가"를 고민하지 않는다.
**이 PoC 에서 만들어 검증한 두 가지가 그대로 쓰인다.**

| 조건 | 어디에 있나 | 무엇을 보나 |
|---|---|---|
| 확인 게이트 | `poc/confirm.py` | 음력 · 윤달 · 자시 경계 · 서머타임 구간 · 시각/출생지 미상 |
| **숫자 대조 경고** | 〃 | 뽑아낸 월·일이 **손님이 적은 값과 어긋남** |
| 안전 계층 | `poc/safety.py` | 금칙어(절대금지·조건부) · 단정 표현(양태) |
| 초안 생성 실패 | 생성기 | 문장이 없으면 보낼 것이 없다 |

하나라도 걸리면 `held` 로 가고 타이머를 타지 않는다.

#### 지금 표본으로 재 본 비율

| | 건수 |
|---|---|
| 자동 발송 | **3** (001·003·006) |
| 사람에게 | **8** |
| 합계 | 11 |

⚠ **이 비율을 그대로 믿으면 안 된다.** 표본을 **일부러 어렵게** 만들었다 —
음력·윤달·자시경계·서머타임을 억지로 밀어 넣었다. 실제 손님은 대부분
`양력 + 시각 안다 + 낮 시간` 이라 훨씬 많이 통과할 것이다. **실제 비율은 아직 모른다.**

#### 게이트가 너무 예민하면

| 지금 | 느슨하게 하면 |
|---|---|
| 음력이면 무조건 사람에게 | 음력 **+ 숫자 대조 경고**일 때만 |
| 자시 경계면 무조건 | 자시 경계 **+ 보정으로 날짜가 넘어갈 때**만 |

풀면 자동 발송이 늘지만 **틀린 원국이 나갈 확률도 는다.** 운영 데이터를 보고 정한다.

### 타이머 규칙

| 항목 | 규칙 |
|---|---|
| 시작 | 초안 생성이 끝난 순간 |
| 길이 | 30분 |
| **영업시간 밖** | **영업 시작 시각부터** 센다. 결제 화면에 미리 안내한다 |
| 보류 후 재개 | 남은 시간이 아니라 **30분을 다시** 센다 |
| 관리자 수정 | 수정만으로는 안 바뀐다. `지금 보내기` 를 눌러야 즉시 |

> **영업시간 밖 규칙이 없으면 설계가 무너진다.** 새벽 주문이 아무도 안 본 채 나가고,
> 그 순간 이 문서의 안전 설계가 전부 무의미해진다.

### 관리자 검수 화면

| 영역 | 요구 |
|---|---|
| 남은 시간 | 크게. **보류 버튼이 바로 옆** |
| 왜 봐야 하나 | 게이트가 잡은 이유를 **맨 위에** |
| 계산 결과 | 원국 8글자·오행·세운 — **고칠 수 없는 영역** |
| 초안 문장 | **여기만 고칠 수 있다.** 누가·언제·무엇을 고쳤는지 남긴다 |
| 손님이 적은 값 | 대조용으로 나란히 |
| 버튼 | `지금 보내기` · `보류` · `다시 생성` |

**계산 결과를 못 고치게 막는 이유** — 그것은 코드가 정한 사실이다.
고쳐야 한다면 **입력값이 틀린 것**이므로 손님에게 되물어야 한다.
손으로 고치면 어디서 틀렸는지 영영 알 수 없게 된다.

### 발송

| 항목 | 규칙 |
|---|---|
| 보내는 것 | **결과 본문이 아니라 링크** |
| 순서 | 알림톡 먼저 → 실패하면 **문자로 대체** |
| 알림톡 제약 | 템플릿 **사전 승인** 필요. 문구를 바꾸면 다시 받는다 |
| 재발송 | 같은 링크. **횟수 제한** |

승인에 시간이 걸리므로 **초기에는 문자만으로 시작**해도 된다.

## 3. 관리자가 고친 것이 곧 품질 점수다

| 세는 것 | 무슨 뜻 |
|---|---|
| 고친 건수 / 전체 | 초안을 그대로 쓸 수 있는 비율 |
| 어느 항목을 자주 고치나 | **그 부분의 프롬프트를 고쳐야 한다** |
| 건당 검수 시간 | **S3 의 진짜 분모** |

> 이 PoC 의 **S5(초안 품질)** 를 운영에서 자동으로 재는 장치다.
> 사람이 따로 채점표를 채우지 않아도 **고친 기록이 곧 점수**가 된다.
> `verify/s5_quality.py` 는 PoC 용이고, 상용에서는 이것이 대신한다.

## 4. PoC 자산의 이관 — 무엇을 가져가나

| PoC 자산 | 상용에서 |
|---|---|
| `poc/confirm.py` 확인 게이트 | **그대로.** 자동 발송 제외 판정에 쓴다 |
| `poc/safety.py` 안전 계층 3층 | **그대로.** 상용의 낱말 목록 11개를 대체한다 |
| `poc/extract.py` 항목 추출 | 그대로. 상담 접수 경로에 |
| `poc/mask.py` 개인정보 마스킹 | 그대로 |
| `spec/fields.yaml` 선언 | 그대로. 문서·채점·구현의 단일 진실 원천 |
| `verify/selftest_negative.py` | **반드시 같이 옮긴다.** 검사 55개 |
| `verify/seal.py` 봉인 | 모델을 바꿀 때마다 재측정하는 근거 |
| `poc/report.py` | **버린다.** 상용 생성기에 사주 분기를 넣어 통합 |
| `engine/` | **버린다.** 복사본이므로 원본을 쓴다 |

### 가장 조용하고 위험한 것

`engine/` 이 상용 저장소의 **복사본**이다. PoC 에서 고친 것이
**상용 코드에는 반영돼 있지 않다.** 이 상태로 상용에 가면
"PoC 에서 검증했다"는 말이 성립하지 않는다.

## 5. 실측으로 확인한 운영 제약

| | 실측 | 뜻 |
|---|---|---|
| 받아쓰기 속도 | 음성 길이의 **1.1~1.6배** (CPU) | 10분 통화면 **11~16분**. GPU 가 필요하다 |
| ② ~ ⑦ | 건당 **10~18초** | 문제가 아니다 |
| 리포트 1건 원가 | 약 **0.9~1.1원** | ⚠ 단가 미확인. 토큰만 실측 |
| 코드 구간 결정성 | **100%** | 같은 입력에 항상 같은 원국 |
| 추출 재현성 | 95.2% | **사람 확인 화면이 필수인 근거** |

**병목은 받아쓰기다.** 기계 시간의 90% 를 차지한다.
GPU 를 쓰거나, **상담 중에 실시간으로** 돌려 통화가 끝나면 받아쓰기도 끝나 있게 해야 한다.

## 6. 아직 정하지 못한 것

| | 무엇 | 왜 못 정했나 |
|---|---|---|
| 1 | 영업시간 밖 타이머 기준 | 실제 운영 시간을 모른다 |
| 2 | 게이트를 어디까지 풀 것인가 | 실제 통과율을 모른다 |
| 3 | 알림톡을 처음부터 쓸 것인가 | 템플릿 승인 기간을 모른다 |
| 4 | 유파 규약 (격국·용신·신살·자시) | **도메인 판단이다.** 정하지 않으면 리포트가 유파를 섞는다 |
| 5 | 개인정보 국외 이전 | LLM API 로 원문이 나간다. **법률 검토가 필요하다** |
| 6 | 본인확인 의무 여부 | 업종별 요건을 확인하지 않았다 |

**4번이 조용히 위험하다.** 같은 원국에서 "억부로는 화가 용신, 조후로는 수가 용신" 같은
모순된 조언이 한 리포트에 나올 수 있다. 계산 오류가 아니라 **일관성 오류**이고,
지금 성적표에서는 전혀 보이지 않는다.
